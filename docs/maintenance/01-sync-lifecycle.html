옛 글에 차례를 빼앗겨
새 글 수정이 밀릴 수 있습니다

Notion에서 옛 글을 블로그 범위 밖으로 옮긴 뒤 새 글을 고쳐도, 앱이 옛 글만 계속 확인 대상으로 고를 수 있습니다. 첫 설치 도중 앱이 꺼지면 재시작 후에도 첫 화면을 준비하지 못하는 경우도 있습니다. 두 문제 모두 다음에 해야 할 일을 제대로 남기고 정리하지 못해서 생깁니다.

2026-10-04단일 사이트 · 갱신 작업은 한 번에 하나현재 아키텍처

원래 기대하는 동작

Notion에서 고치면, 다음 확인 때 블로그도 바뀌어야 합니다

블로그 주인이 Notion의 「여행 기록」을 블로그의 시작 페이지로 지정했다고 가정합니다. 앱은 이 페이지와 그 아래에 실제로 들어 있는 페이지를 가져옵니다. 이 문서에서는 그 묶음을 블로그 범위라고 부릅니다. 본문에 다른 페이지의 링크만 붙이는 것으로는 이 범위가 넓어지지 않습니다.

  1. 처음에는 내용을 가져옵니다앱이 「여행 기록」과 하위 페이지를 수집합니다. 확인을 마친 글 중 게시된 글을 독자에게 보여 줍니다.
  2. 이후에는 다시 확인합니다앱은 무엇을 언제 다시 가져올지 목록에 기록합니다. 글이 수정되었는지, 아래에 새 페이지가 생겼는지 주기적으로 확인합니다.
  3. 범위가 바뀌면 목록도 바뀌어야 합니다범위 밖으로 옮긴 글은 확인 목록에서 빠지고, 남아 있는 글은 계속 확인해야 합니다. 중간에 앱이 꺼져도 끝내지 못한 일은 다시 시작해야 합니다.

이 문서에서 말하는 문제

블로그 주인: 옛 글을 정리한 뒤 「겨울 여행」을 고쳤는데 블로그에는 수정 전 내용이 남을 수 있습니다. 첫 설치 중 앱이 꺼진 경우에는 다시 켜도 초기화가 끝나지 않을 수 있습니다.

독자: 새 내용을 기다려도 예전 내용만 보거나, 첫 방문부터 ‘아직 준비되지 않음’을 뜻하는 503 응답을 계속 받을 수 있습니다.

개발자: 앱이 실행 중이라는 사실만으로 갱신도 진행된다고 판단할 수 없습니다. 불필요한 확인 기록이 남았는지, 필요한 첫 작업의 기록이 빠졌는지를 찾아야 합니다.

왜 지금 살펴볼까요? 글을 옮기는 일과 앱 재시작은 평범한 운영 작업입니다. 이런 상황에서 갱신이 멈출 수 있는 틈을 남겨 두면, 새 기능이 확인 목록을 더 많이 만들 때 같은 문제가 생길 곳도 늘어납니다.

두 가지 구체적인 상황

필요 없는 일은 남고, 꼭 필요한 첫 일은 빠집니다

1. 옛 여행 글을 옮겼더니 「겨울 여행」의 수정이 밀립니다

설명을 위해 한 회차에 3개만 확인한다고 가정합니다. 실제 기본값은 100개이며, 아래 이름·시각·개수는 동작을 보여 주기 위한 예시입니다.

  1. 주인이 옛 글 세 개를 범위 밖으로 옮깁니다「여행 기록」 아래의 「봄 여행」·「여름 여행」·「가을 여행」을 다른 곳으로 옮기고 「겨울 여행」을 넣습니다. 앱이 새 구성을 수집해 반영한 뒤, 주인이 「겨울 여행」의 내용을 한 번 더 고칩니다.
  2. 블로그 범위는 바뀌었는데 확인 목록은 덜 정리되었습니다옛 글 세 개는 더 이상 블로그에 속하지 않습니다. 하지만 ‘09:00에 다시 확인’이라는 기록은 남아 있습니다. 「겨울 여행」과 「여행 기록」, ‘범위 전체 확인’은 09:05에 확인할 차례입니다.
  3. 09:10에 앱이 옛 기록 세 개를 먼저 고릅니다예정 시각이 가장 이른 기록부터 3개를 고르므로 옛 글이 모든 자리를 차지합니다. 앱은 고른 뒤에야 각 글이 범위 밖이라는 사실을 확인하고 작업을 건너뜁니다.
  4. 건너뛴 기록이 그대로여서 다음에도 같은 세 개를 고릅니다앱은 기록을 지우지도, 다음 확인 시각을 뒤로 옮기지도 않습니다. 계속 09:00이 가장 이르므로 「겨울 여행」의 수정 내용을 가져올 차례가 오지 않을 수 있습니다.
한 번 건너뛴 뒤에도 다음 회차가 나아지지 않는 이유
시점정상이라면현재 코드의 이 예시에서는
새 범위를 반영한 뒤옛 글 세 개의 확인 기록을 없앱니다.블로그 범위에서만 빠지고, 확인 기록은 남습니다.
09:10에 고르는 3개「겨울 여행」, 「여행 기록」, 범위 전체 확인「봄 여행」, 「여름 여행」, 「가을 여행」 → 모두 건너뜁니다.
다음 회차에 고르는 목록아직 실행할 항목이 없습니다. 「겨울 여행」·「여행 기록」·범위 전체 확인은 새 예정 시각까지 기다립니다.다시 「봄 여행」, 「여름 여행」, 「가을 여행」 → 필요한 세 작업은 계속 뒤에 남습니다.

예시에서는 바로 다음 회차에 새 작업의 차례가 오지 않고, 정상 확인한 작업도 아직 다시 확인할 때가 아니라고 가정합니다. 설정을 다시 읽을 시각은 09:20입니다. 같은 시각인 작업끼리의 내부 정렬 순서는 생략했습니다. 옛 기록이 제한 개수 이상이고 필요한 작업보다 앞에 있을 때 이런 막힘이 생깁니다. 필요한 기록이 더 이르면 먼저 실행될 수 있으므로, 글을 하나 옮길 때마다 모든 갱신이 멈춘다는 뜻은 아닙니다.

어디가 어긋났나요?

앱은 ‘블로그에 속한 글’과 ‘다시 확인할 목록’을 따로 저장합니다. 새 범위를 적용할 때 뒤의 목록을 정리하지 않고, 매번 개수를 먼저 자른 다음 필요 없는 일을 걸러 냅니다. 걸러 낸 자리만큼 다른 일을 다시 뽑지도 않습니다. 그래서 확인 횟수를 늘리는 것만으로는 옛 기록이 쌓이는 원인이 없어지지 않습니다.

범위 밖으로 옮긴 글과, 범위 안에서 게시만 중단한 글은 다릅니다.

「봄 여행」처럼 범위에서 빠진 글의 확인 기록은 정리해야 합니다. 반면 「겨울 여행」을 같은 위치에 두고 잠시 게시만 중단했다면 계속 확인해야 합니다. 그래야 다시 게시했을 때 알아차릴 수 있습니다.

위 예시는 새 범위 반영이 끝난 뒤의 갱신 지연 문제입니다. 남은 확인 기록 때문에 범위 밖 글이 독자에게 다시 노출되는 문제는 아닙니다. 글을 보여 줄 때는 현재 블로그 범위와 게시 여부를 별도로 확인합니다.

여기서 inactive는 활성 범위 밖이라는 뜻입니다. loadPost는 UNPUBLISHED를 제외하지 않습니다. 미게시 부모 아래의 후손도 수집하며, 본문 링크는 범위 구성원을 만드는 근거가 아닙니다.

새 범위를 끝내 수집하지 못한 경우에도 잔여 행이 생길 수 있습니다. 새 글 「숙소 안내」를 저장한 뒤 다른 자식 수집이 실패하면, 새 범위 버전은 폐기해도 「숙소 안내」의 Post 예약은 남습니다. 제한을 적용한 뒤 필터링하거나 배치 크기만 키우는 조치는 이 누적 원인을 없애지 못합니다.

2. 첫 설치 도중 꺼진 뒤, 다시 켜도 블로그가 준비되지 않습니다

이번에는 내용이 한 번도 수집되지 않은 새 설치입니다. 정상이라면 「여행 기록」을 시작 페이지로 저장하고, 곧이어 내용을 가져와 첫 화면을 준비해야 합니다.

  1. 앱이 ‘시작 페이지는 「여행 기록」’이라고 저장합니다설정을 읽는 일은 성공으로 기록합니다. 하지만 실제 내용을 가져오는 일은 아직 시작하지 않았고, 나중에 다시 실행할 작업으로도 저장하지 않았습니다.
  2. 바로 다음 내용을 수집하려는 순간 앱이 꺼집니다설정 저장과 첫 내용 수집은 별개의 단계입니다. 둘 사이에서 종료되면, 저장된 시작 페이지만 남습니다.
  3. 재시작 후 설정을 다시 읽어도 같은 페이지입니다현재 코드는 시작 페이지가 바뀌었을 때만 이어서 내용 수집을 요청합니다. 이미 「여행 기록」이 저장되어 있으므로 ‘변경 없음’으로 보고 수집을 요청하지 않습니다.
  4. 설정은 맞는데, 끝내지 못한 첫 수집을 다시 맡길 곳이 없습니다별도로 수집을 실행하거나 시작 페이지를 바꾸는 일이 없다면, 첫 화면은 계속 초기화 중일 수 있습니다. 독자의 요청에는 503 응답이 돌아갑니다.

어디가 어긋났나요?

‘설정을 저장했다’는 사실만 남기고, ‘이 설정으로 첫 내용을 가져와야 한다’는 일을 남기지 않았습니다. 같은 설정을 다시 읽는 것만으로는 이 빠진 일을 알아차리지 못합니다. 내용 수집을 완료하지 않은 상태도 찾아내거나, 수집 요청을 종료 후에도 남는 기록으로 저장해야 합니다.

이것은 첫 수집의 재실행 기록이 생기기 전에 끊기는 특정 공백입니다. 모든 재시작이나 모든 Notion 장애가 같은 결과를 낳는다는 뜻은 아닙니다. 이미 전체 수집의 다음 실행 기록이 있는 사이트는 그 기록으로 다시 시도할 수 있습니다.

개발자용 근거: 첫 설정 저장, 비어 있는 공개 범위, DB 오류의 차이

V2 migration은 SITE_CONFIGURATION의 due 행만 넣습니다. ApplyImportedSiteConfigurationService.apply는 최초 설정과 activeRevisionId = null인 BlogPublication, 설정 성공 상태를 같은 트랜잭션에서 저장합니다. publication 동기화 행은 만들지 않습니다. 첫 rootChanged = true는 반환값이고, 트랜잭션 종료 뒤 SynchronizeSiteConfigurationService가 이를 보고 직접 수집을 호출합니다. 재시작 후 같은 루트는 rootChanged = false입니다. 설정 근거

publication 행의 존재만으로 첫 수집 완료를 판단하면 안 됩니다. 행이 있어도 activeRevisionId == null이면 활성화한 범위가 아직 없습니다. 이때 루트와 유효한 게시글 경로의 읽기는 ContentUnavailable이고 웹에서는 503입니다. 잘못된 내부 ID는 별도로 404 처리됩니다. HTTP 변환 근거

SynchronizePublicationService의 begin은 try 밖에 있습니다. 첫 begin의 DB 저장 실패는 publication 실패 예약을 만들지 못합니다. begin 뒤 일반 DB RuntimeException으로 apply가 실패해도 현재 catch 대상이 아니므로 수집 중 버전인 STAGING이 남을 수 있습니다. 다음 begin은 이를 ABANDONED로 바꾸지만, 첫 예약이 없다면 다음 begin 자체를 시작하지 못합니다. 호출 순서, 다음 begin의 정리

반면 현재 catch로 분류한 소스·검증 실패는 abandon을 통해 publication 실패 상태와 다음 재시도 시각을 저장합니다. 또한 이미 SyncTarget.Publication 행이 있는 경우에는 그 실행 기록이 남습니다. ‘publication 데이터가 있음’과 ‘publication 실행 예약이 있음’은 서로 다릅니다.

두 이야기의 결과는 현재 소스 흐름과 기존 테스트를 읽고 추론했습니다. 이번 작업에서 장애를 재현하거나 애플리케이션 테스트를 실행하지 않았습니다.

확인할 글은 빠뜨리지 않고, 끝내지 못한 일은 다시 시작합니다

  • 범위 밖 글이 필요한 작업의 차례를 막아서는 안 됩니다. 범위 안에서 게시만 중단한 글은 계속 확인합니다.
  • 첫 설치나 시작 페이지 변경으로 생긴 수집 작업은 앱이 꺼져도 잊지 않아야 합니다. DB가 복구되면 다시 시도할 수 있어야 합니다.
  • 전체 수집이 끝나지 않은 새 범위를 완성된 것으로 취급하지 않습니다. 다음 시도에서 새로 수집하며, 그동안 기존에 확인한 범위를 유지합니다.
  • 실패 후 정해 둔 대기 시간은 지킵니다. 정리 작업이 이를 매번 없애서 Notion에 요청을 쏟아내면 안 됩니다.

비교의 전제: 한 사이트의 갱신 작업은 한 번에 하나씩 실행하며, 수동 실행도 같은 규칙을 따릅니다. 여러 서버가 동시에 실행하거나 수집 도중 설정을 바꾸는 경쟁까지 이 세 제안이 해결하는 것은 아닙니다.

개발자용 공통 제약: 저장 단위와 중단 후 처리

조회는 짧은 읽기 전용 트랜잭션, 결과 반영은 application 쓰기 서비스의 짧은 트랜잭션으로 처리합니다. 외부 HTTP 호출 중 DB 트랜잭션을 유지하지 않습니다. 현재 스케줄러의 AtomicBoolean은 같은 인스턴스의 중복 실행만 막습니다.

게시글 하나의 불완전한 블록 트리는 저장하지 않고, 전체 범위를 검증한 뒤 활성 포인터를 교체합니다. 범위 수집 중 완성된 개별 게시글의 내용·게시 상태는 먼저 저장될 수 있습니다. 범위 버전의 원자성과 모든 게시글 내용의 동시 교체를 혼동하지 않습니다.

남은 STAGING은 다음 begin에서 폐기합니다. ABANDONED 구성원 기록, 보관된 게시글·스냅샷의 물리 삭제와 보존 기간은 별도 정책입니다. 소스 중립 도메인, 단일 Spring Boot 이미지, 기존 실패 분류와 오래된 콘텐츠 제공을 유지합니다. 별도 worker, broker, 범용 이벤트 버스, 복잡한 잠금·SQL을 전제로 하지 않습니다.

해결책 A

범위가 바뀔 때 확인 목록도 함께 고칩니다

설정이나 블로그 범위를 저장하는 코드가, 그 변화로 생기거나 없어지는 확인 작업도 함께 저장합니다. 변경 내용과 다음 할 일이 둘 다 남거나, 둘 다 남지 않도록 묶는 방식입니다.

  • 옛 글 이야기: 새 범위를 적용하는 순간 「봄 여행」·「여름 여행」·「가을 여행」의 확인 기록을 빼고 「겨울 여행」의 기록을 보장합니다. 다음 회차에는 필요한 일을 고를 수 있습니다.
  • 첫 설치 이야기: 「여행 기록」 설정과 ‘첫 내용 수집’ 작업을 함께 저장합니다. 그 직후 꺼져도 재시작하면 할 일이 남아 있습니다. 실제 수집을 끝내기 전에는 성공으로 처리하지 않습니다.

개발자가 기억할 일

대상을 추가하거나 제거하는 모든 저장 경로에서 확인 목록도 바꿔야 합니다. 예를 들어 나중에 첨부파일 갱신 기능을 넣는다면, 첨부파일을 등록·제거하는 코드가 확인 작업의 등록·제거까지 맡습니다. 새 경로 하나에서 빠뜨리면 같은 문제가 다시 생길 수 있습니다.

이점과 비용: 글마다 다른 확인 주기와 실패 후 대기 시간을 유지할 수 있고, 변경과 작업 기록이 함께 남는지 확인하기 쉽습니다. 대신 설정 저장·글 저장·범위 적용의 역할을 정확히 나눠야 합니다. 도입할 때는 이미 남은 옛 기록과 빠진 기록도 한 번 대조해 정리해야 합니다.

개발자용 변경 범위와 검증 항목

설정 apply는 최초 설정 또는 루트 변경 때 publication의 sync 행을 즉시 due로 만들고 설정과 함께 커밋합니다. 설정이 같으면 기존 예약과 백오프를 덮어쓰지 않습니다. begin은 예약을 소비하거나 미래로 미루지 않습니다. activate 성공 또는 분류된 실패를 기록할 때만 다음 시각을 바꾸므로, 프로세스 종료나 첫 begin의 DB 실패 뒤에도 실행 입구가 남습니다.

Post import는 콘텐츠 확인 기록과 활성 대상의 지속 예약을 구분합니다. 새 STAGING에만 속한 Post의 예약을 무조건 만들지 않습니다. activate는 새 구성원(UNPUBLISHED 포함)의 행을 보장하고 새 집합 밖의 Post 행을 제거합니다. 기존 활성 구성원의 갱신 상태는 유지할 수 있습니다. 저장소의 작은 조회·삭제·upsert와 구체적인 예약 도우미로 구성합니다.

수집 실패로 새 「숙소 안내」가 활성화되지 않았다면 지속 예약도 남기지 않습니다. 미완성 STAGING 정리는 기존 begin을 재사용합니다. refresh_after만으로 루트 변경 요청을 표현하므로, 실행 중 다른 쓰기가 요청을 덮어쓰는 경쟁은 앞의 직렬 실행 전제 밖입니다.

구현 시 검증: 설정과 예약의 원자적 롤백, 범위 교체와 옛 예약 제거, 첫 begin 실패 후 재시작, 미게시 후 재게시 발견, 실패한 STAGING 전용 예약이 남지 않는지를 테스트합니다.

해결책 B

매번 실행 전에, 오늘의 범위와 확인 목록을 맞춥니다

확인할 3개를 고르기 전에 현재 저장된 설정·블로그 범위와 전체 확인 목록을 대조합니다. 빠진 작업은 넣고, 더 이상 필요 없는 작업은 뺍니다. 목록을 고치는 일을 매 회차의 첫 단계로 두는 방식입니다.

  • 옛 글 이야기: ‘현재 「여행 기록」 아래에는 「겨울 여행」만 있다’는 사실을 기준으로 옛 글 세 개의 기록을 먼저 지웁니다. 그다음 작업을 고르므로 세 자리가 낭비되지 않습니다.
  • 첫 설치 이야기: 설정은 있지만 아직 한 번도 내용 수집을 마치지 않았다는 사실을 찾아냅니다. 빠진 ‘첫 내용 수집’ 기록을 복원하므로 같은 시작 페이지여도 다시 시작할 수 있습니다.

개발자가 기억할 일

무엇이 지금 필요한 대상인지 판정하는 규칙을 대조 단계에 빠짐없이 넣어야 합니다. 나중에 첨부파일 갱신 기능을 넣으면, 현재 사용 중인 첨부파일 목록을 읽고 확인 목록과 맞추는 구간을 추가합니다. 첨부파일이 필요한지 판단하는 규칙은 그 기능이 맡습니다.

이점과 비용: 여러 코드 경로에서 빠뜨리거나 남긴 기록을 반복해서 바로잡을 수 있습니다. 대신 매 회차 전체 대상 목록을 읽고 비교하는 비용이 들며, 이 정리에 실패하면 그 회차의 갱신도 미룹니다. 정리한 뒤 새로 생긴 잔여 기록은 다음 회차까지 남을 수 있습니다.

주의할 두 가지: 비교 자체를 처음 3개로 잘라서는 안 됩니다. 또 실패해서 기다리기로 한 작업을 매번 ‘즉시 실행’으로 되돌려서는 안 됩니다. 시작 페이지 변경을 저장할 때는 수집 요청도 함께 기록하고, 이후 대조는 정해진 재시도 시각을 존중합니다.

개발자용 변경 범위와 검증 항목

application 보정 서비스가 설정 singleton, 설정에 연결된 publication, 활성 Post 집합을 원하는 대상으로 계산합니다. sync 저장소에 목록 조회·삭제를 추가하고 누락 행만 due로 생성하며, 불필요한 Post 행을 제거합니다. 기존 행의 성공 주기·백오프는 보존합니다. 스케줄러는 보정 서비스 호출과 due 실행만 맡습니다.

publication의 활성 버전이 없거나 activeRevisionId == null이거나, 설정 루트와 활성 루트의 소스 바인딩이 다르면 수집이 필요한 상태입니다. 루트 변경 시 설정 apply가 publication due 갱신도 함께 커밋하도록 보강합니다. 반복 보정은 누락 행을 복원하고, 이미 행이 있으면 그 시각을 지켜 실패 백오프를 무너뜨리지 않습니다. A와 호환되는 원자적 의도 기록을 포함하지만, 장기 책임의 중심은 반복 대조에 둡니다.

STAGING 전용 Post는 원하는 집합에 넣지 않습니다. 기존 import가 이런 행을 만들더라도 다음 회차에 제거할 수 있어 쓰기 경로 수정은 줄어듭니다. due 제한 전에 전체 대조를 마치며, 보정 실패 시 due 실행을 중단합니다. 규모가 커져 대조를 나눠 수행하려면 전체를 빠짐없이 확인하는 별도 설계가 필요합니다. 재진입한 begin은 미완성 STAGING을 폐기합니다.

구현 시 검증: 옛 기록이 배치보다 많은 경우, 첫 publication 예약 복원, 보정을 반복해도 같은 결과가 되는지, 백오프 보존, 보정 DB 실패, STAGING 전용 대상 제외를 테스트합니다. 범용 플러그인 등록기는 추가하지 않습니다.

해결책 C

사이트 전체를 확인하는 한 주기를 반복합니다

글마다 따로 확인할 차례를 기록하는 대신, ‘이 사이트를 다시 확인한다’는 작업 하나를 반복합니다. 한 주기에 설정을 읽고 시작 페이지부터 현재 하위 페이지의 내용을 가져옵니다. 여기서는 비용을 비교하기 위해 시작 페이지가 같아도 매 주기 전체를 다시 수집하는 안을 기준으로 합니다.

  • 옛 글 이야기: 「여행 기록」의 현재 하위 페이지를 따라가므로 「겨울 여행」을 가져옵니다. 옛 글별 확인 기록으로 순서를 고르지 않아 「봄 여행」 등이 차례를 차지할 수 없습니다.
  • 첫 설치 이야기: 설정 저장만 끝났다고 한 주기의 성공으로 보지 않습니다. 첫 수집을 끝내기 전에 꺼졌다면, 남아 있는 사이트 작업을 통해 같은 시작 페이지에서도 다시 수집합니다.
첫 작업 기록은 첫 설정을 읽기 전에 저장해야 합니다.

‘사이트 전체를 확인할 일’을 종료 후에도 남도록 먼저 저장한 뒤 설정 수집을 시작해야 합니다. 기존 설치를 이 방식으로 바꿀 때도 같은 준비가 필요합니다. 이 기록 없이 설정부터 읽으면 두 번째 이야기의 빈틈이 다시 생깁니다.

설정이나 블로그의 기본 기록이 있다는 사실만으로 완료를 판단하지 않습니다. 실제로 사용할 범위를 한 번도 완성하지 못했다면 아직 할 일이 남은 상태입니다.

개발자가 기억할 일

사이트 작업의 시작·완료·실패 후 대기 시점을 한곳에서 관리해야 합니다. 나중에 첨부파일 확인 기능을 넣으면 이 주기의 한 단계로 추가합니다. 다만 첨부파일은 더 자주 확인하거나, 그 실패가 글 갱신을 늦추지 않아야 한다면 별도 상태가 늘어납니다. 그런 요구가 많아지면 A나 B를 다시 검토할 이유가 됩니다.

이점과 비용: 글별 확인 목록을 맞추는 일이 줄어듭니다. 대신 매 주기 모든 하위 페이지를 읽으므로 Notion 호출과 실행 시간이 늘어납니다. 느리거나 실패한 페이지 하나가 전체 주기의 완료와 뒤에 있는 글의 갱신을 늦출 수 있고, 글마다 다른 주기와 재시도 간격을 주기도 어려워집니다.

설정을 읽지 못했을 때 이전 설정으로 내용 수집을 계속할지, 그 회차를 실패로 끝낼지는 채택 전에 정해야 합니다. 아직 저장된 설정조차 없는 첫 설치라면 기다렸다가 다시 시도합니다. 일부 수집을 생략하는 최적화는 이 비교에 포함하지 않았습니다.

개발자용 변경 범위, 최초 예약, 검증 항목

사이트 application 오케스트레이터가 저장된 사이트 수준 실행 시각·실패 상태를 보고 진입합니다. 기존 sync_state에 사이트 실행 종류를 추가하고 조회·실행 경로를 바꿉니다. 설정 pull 성공 시각과 사이트 전체 진행 시각을 분리하고, publication 활성화까지 끝나야 사이트 성공을 기록합니다. 외부 HTTP 동안 DB 트랜잭션을 유지하지 않습니다.

현재 V2 seed는 SITE_CONFIGURATION만 등록하므로 새 사이트 실행을 시작시키기에 충분하지 않습니다. 새 사이트 실행 singleton의 due 행을 첫 설정 fetch보다 먼저 내구성 있게 저장해야 합니다. 기존 migration을 고치지 않고 추가 전용 부트스트랩 마이그레이션으로 보장하며, 기존 설치의 전환에도 적용합니다. 예약이 준비된 뒤에만 설정 수집을 시작합니다.

최소한 publication 행 부재, activeRevisionId == null, 설정 루트와 활성 루트의 소스 바인딩 불일치는 모두 수집이 필요한 상태입니다. publication 행만 있고 활성 revision이 없으면 미완료입니다. 여기서 비교하는 ‘매 주기 전체 재수집’ 정책은 이 조건들을 포함해 항상 수집하며, 모든 후손의 Post를 저장하므로 글별 갱신을 따로 반복하지 않습니다.

전환 시 옛 Post 예약을 정리하고 이후 Post apply가 실행 큐 행을 만들지 않게 합니다. STAGING 전용 게시글 저장은 가능하지만 별도 예약은 만들지 않습니다. begin의 미완성 버전 폐기는 재사용합니다. 분류된 실패에는 사이트 백오프를 기록하고, 종료나 DB 장애로 실패를 기록하지 못하면 기존 due를 남깁니다.

활성화 커밋 뒤 사이트 성공 기록 전에 중단되면 다음에 같은 내용을 다시 수집할 수 있습니다. 조회·저장과 새 revision 생성을 반복해도 안전하도록 만들며, 정확히 한 번만 실행된다고 약속하지 않습니다. 수집 실패 시 기존 활성 범위를 유지하는 것과 개별 글의 갱신 지연은 별개의 문제입니다.

구현 시 검증: 빈 DB의 첫 예약과 재시작, 설정 저장 후 종료, 활성화 후 종료, 반복 실행, 느린 자식의 영향, 미게시 후 재게시, 외부 HTTP 중 트랜잭션 부재를 테스트합니다.

선택 기준

글마다 따로 갱신할 필요가 얼마나 큰지부터 봅니다

기존 흐름을 유지하면서 글마다 확인 주기와 실패 후 대기 시간을 다르게 관리하려면 A를 우선 검토할 수 있습니다. 대상을 만드는 경로가 늘고 자동 복구도 필요하면 B의 반복 대조 비용을 받아들일 이유가 생깁니다. 글이 적고 매번 전체를 읽는 비용을 감당할 수 있으면 C도 후보입니다.

실제 글 수, 허용할 갱신 지연, Notion 요청량의 한도가 주어지지 않았으므로 여기서 하나를 확정하지 않습니다. 세 안 모두 두 이야기를 해결해야 하며, ‘개수를 더 많이 뽑기’나 ‘일단 한 번 재시작하기’만으로 끝내서는 안 됩니다.

구현을 선택한 뒤의 진행 순서
  1. 첫 수집 요청이 사라지는 경우와 옛 기록이 배치 크기 이상인 경우를 실패 테스트로 고정합니다. 중단 지점은 DB 커밋 전후로 나눕니다.
  2. 선택한 책임과 재시도 정책을 아키텍처 문서에 먼저 반영합니다. A/B는 요청 저장의 원자성을, C는 첫 예약과 사이트 완료 시점을 명시합니다.
  3. 짧은 트랜잭션과 작은 저장소 연산으로 구현합니다. 기존 잔여·누락 기록은 대조해 보정하고, STAGING은 다음 begin에서 폐기합니다.
  4. 설정 저장·begin·Post apply·activate 사이의 중단, DB 복구 후 재실행, 미게시 후 재게시를 검증합니다. ABANDONED 기록의 장기 보존 기간은 별도 운영 정책으로 둡니다.

직접 호출은 빠른 실행 수단으로 남길 수 있지만, 저장 후 중단된 일을 복구하는 유일한 수단으로 삼지 않습니다. 특정 예약을 보장하는 작은 구체 도우미는 가능하며, 가상의 미래 기능만을 이유로 범용 프레임워크를 만들지는 않습니다.

코드를 읽을 때 필요한 짧은 용어 풀이
  • sync_state: 대상을 언제 다시 확인할지와 성공·실패 상태를 저장한 기록입니다. 본문의 ‘확인 목록’에 해당합니다.
  • due: 저장된 다음 시각이 되어 지금 실행할 차례라는 뜻입니다. backoff는 실패 뒤 다음 시도까지 두는 대기 시간입니다.
  • publication / revision: 블로그 범위와 그 범위를 수집한 버전입니다. activeRevisionId는 현재 사용할 완성된 버전을 가리킵니다.
  • STAGING / ACTIVE / ABANDONED: 각각 수집 중인 범위, 사용할 범위, 사용하지 않기로 한 미완성 범위입니다. 범위 안 글의 게시 여부와는 별개입니다.
