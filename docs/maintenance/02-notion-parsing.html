정상적인 사진과 글은 지금도 읽을 수 있습니다

운영자가 Notion에 「주말 산책」을 쓰고 사진을 넣었다고 가정합니다. 공개 범위와 게시 조건을 갖춘 글이라면, 블로그는 Notion에서 제목·본문·사진 정보를 가져와 저장하고 독자에게 보여 줍니다. 사진 주소에 유효 기간이 있으면 그 만료 시각도 함께 읽습니다.

  1. 운영자가 글을 고칩니다「주말 산책」에 사진과 설명을 추가합니다.

사례 · 행동에서 결과까지

두 사례를 따라가면 고쳐야 할 지점이 보입니다

1. 새 표시 옵션을 추가했는데 읽어 오지 않습니다

가상 기능입니다. 향후 Notion 응답에 코드 블록의 “줄 번호 표시” 옵션이 생기고, 블로그가 이를 지원하려 한다고 가정합니다. 현재 Notion API에 그 옵션이 있다는 주장은 아닙니다. 목표는 「설치 방법」 글의 코드 옆에 줄 번호를 표시하는 것입니다.

  1. 개발자가 데이터 모양을 적은 선언을 찾습니다코드 블록의 언어·설명 같은 항목이 모여 있어 새 옵션도 여기에 추가하면 읽힐 것이라 생각합니다.
  2. 그 선언에 “줄 번호 표시” 항목을 추가합니다새 응답을 받으면 이 값이 블로그 내부로 전달될 것으로 기대합니다. 이후 저장과 화면 표시까지 연결하려는 첫 단계입니다.
  3. 하지만 실행되는 코드는 그 선언을 쓰지 않습니다현재 변환 코드는 Notion이 보낸 자료에서 본문·언어·설명을 직접 꺼냅니다. 수정한 선언을 거치지 않으므로 새 옵션을 읽는 동작도 생기지 않습니다.
  4. 개발자는 실제 읽기 경로를 다시 찾아야 합니다선언만 바꾼 상태에서는 전달되는 값도, 독자가 보는 결과도 그대로입니다. 실제 입력을 읽는 곳을 찾아 고치고 저장·표시까지 연결해야 합니다.

어디가 어긋났나. “자료가 이런 모양이다”라고 적어 둔 곳과 “들어온 자료를 이렇게 읽는다”는 실행 코드가 따로 있습니다. 앞의 선언을 DTO라고 부릅니다. DTO는 값을 담을 모양이며, 입력을 검사하고 그 모양의 값을 만드는 디코더와는 다릅니다. 선언을 추가하는 것만으로 입력이 읽히거나 검사되지는 않습니다.

현재 일부 블록·글자 꾸밈용 선언은 실제 읽기 경로에 연결되지 않았습니다. 기존 테스트가 이 미사용 선언을 자동으로 검증한다는 뜻도 아닙니다. 이 사례의 손해는 잘못된 곳을 먼저 고치는 시간과, 기능을 연결했다고 오해할 가능성입니다.

실제 코드와 대응하면: 어떤 선언이 쓰이지 않는가

NotionTextBlockData에는 language와 caption 등이 있습니다. 하지만 NotionBlockMapper.mapContent의 code 분기는 payload의 rich_text·language·caption을 직접 읽습니다. JsonNode는 이처럼 필드 이름으로 탐색하는 JSON 자료 구조입니다.

dto/block의 다섯 파일과 dto/richtext의 두 파일에 선언된 클래스 이름을 src 전체에서 검색했습니다. 참조는 해당 파일군의 선언과 상호 참조뿐이었으며, 실제 변환이나 테스트의 사용은 발견되지 않았습니다. 페이지·블록의 공통 정보 등을 담는 다른 DTO까지 모두 미사용이라는 뜻은 아닙니다. 근거 S1·S2·S6

앞으로 가상 옵션을 구현한다면 실제 응답 입력 → 값 읽기 → 도메인 값 → 저장 형식 → 화면 표시를 확인해야 합니다. DTO를 생성하는 테스트만으로 이 전체 연결을 확인할 수는 없습니다. 이번 작업에서는 새 기능이나 테스트를 추가하지 않았습니다.

2. 같은 숫자 42인데, 사진을 쓰는 위치에 따라 결과가 갈립니다

정상 시각 문자열과 누락된 만료 정보는 앞의 표처럼 처리됩니다. 이제 「주말 산책」의 사진에 똑같이 잘못된 만료값 42가 들어왔다고 가정합니다. 본문 사진으로 읽는 경우와 갤러리 카드의 대표 사진으로 읽는 경우를 비교합니다.

  1. 앱이 같은 사진 정보와 숫자 42를 받습니다주소는 정상이고, 만료 항목만 잘못되었습니다. 기대하는 것은 사용 위치가 달라도 이 입력의 옳고 그름을 같은 규칙으로 판단하는 것입니다.
  2. 본문에서는 “읽을 시각이 없다”고 넘어갑니다문자열만 꺼내는 코드가 숫자를 걸러 내고 빈 결과를 반환합니다. 다음 단계는 이를 항목이 아예 없었던 경우와 구별하지 못합니다.
  3. 커버에서는 “값의 형식이 틀렸다”고 멈춥니다사진을 변환하기 전에 별도 검사 코드가 실행됩니다. 이 코드는 숫자가 온 사실을 오류로 처리합니다.
  4. 반영되는 결과도 달라집니다본문은 만료 시각 없이 변환될 수 있습니다. 커버는 그 갤러리를 포함한 글의 가져오기를 실패시켜 새 내용 저장을 막습니다. 기존에 공개 중인 글이라면 마지막 정상 내용을 유지합니다.
입력은 동일하고, 읽는 코드만 다릅니다
위치만료값 42에 대한 판단예상되는 영향
일반 본문 사진만료 정보가 없는 것으로 처리합니다.잘못된 입력을 놓칩니다. 만료 시각이 없으므로 그 시각을 기준으로 사진 주소를 제외할 수 없습니다.
갤러리 커버잘못된 입력으로 거부합니다.해당 글의 새 내용 반영이 멈춥니다. 이미 정상 저장된 내용은 보존합니다.

어디가 어긋났나. 같은 만료 정보를 읽는 코드가 두 군데에 있고, 한쪽은 “없음”과 “잘못됨”을 합치고 다른 쪽은 구분합니다. 화면 위치 때문에 추가 검사가 필요한 경우는 있지만, 이 차이가 의도한 규칙인지는 명확히 정해야 합니다.

확인 범위: 위 결과는 현재 코드를 읽어 추론한 것입니다. 커버가 숫자 42를 거부하는 기존 테스트는 확인했지만 이번에 실행하지 않았습니다. 본문과 커버를 함께 넣은 실행 재현이나 실제 운영 장애를 확인한 것은 아닙니다. 사진이 실제로 깨져 보인다고 단정하지도 않습니다.
동일한 입력과 두 코드 경로 
{"type":"file","file":{"url":"https://images.example/a.png","expiry_time":42}}

본문의 mapMediaSource는 file.optionalText("expiry_time")?.let(::parseInstant)를 호출합니다. 여기의 optionalText는 문자열이 아닌 값을 null로 만들어 시각 해석을 건너뛰고 SourceHosted(expiresAt = null)을 만듭니다.

커버의 media는 같은 mapMediaSource를 부르기 전에 validateExpiry를 실행합니다. 커버 쪽 optionalText가 숫자를 거부해 NotionBlockMappingException이 발생합니다. 즉, 사진 변환 코드를 공유하더라도 그 앞의 검사가 다릅니다. 근거 S2·S5

누락과 명시적 null은 두 경로 모두 만료 시각 없이 허용합니다. 빈 문자열·공백 문자열은 본문에서는 누락처럼 처리하고 커버에서는 거부합니다. 정상 시각 문자열은 양쪽이 보존하며, 비어 있지 않지만 시각 형식이 잘못된 문자열은 본문도 거부합니다.

표시 코드의 mediaUrl은 만료 시각이 없으면 만료 판정으로 URL을 제외하지 않습니다. 이는 영구 URL이라는 보증도, 원격 이미지 요청이 성공한다는 보증도 아닙니다. 커버 오류는 NotionPostSource.fetch에서 소스 매핑 실패로 변환되고, 개별 글 갱신은 실패 상태만 기록합니다. 근거 S3·S8·S10

현재 응답이 글로 바뀌는 경로와 다른 필드의 차이
  1. NotionApiClient가 HTTP 응답을 JsonNode로 받습니다.
  2. parsePage는 공통 정보의 DTO를 만들되 properties·icon·cover는 JSON 자료로 남깁니다. parseBlockPage는 type에 해당하는 객체를 NotionBlockEnvelope.payload에 넣습니다.
  3. 페이지·블록 매퍼가 JSON에서 필드·시간·URL을 직접 읽어 블로그의 값으로 바꿉니다.
  4. NotionPostSource.fetch는 수집을 끝내고 BlockTree를 담은 소스 중립 ImportedPost를 반환합니다.

client의 nullableText는 누락·null을 허용하고 숫자는 거부합니다. block mapper의 optionalText는 누락·null·숫자·빈 문자열을 null로 바꿉니다. optionalArray와 optionalObject도 잘못된 타입을 누락처럼 처리합니다. 비슷한 함수명이 같은 정책을 뜻하지 않습니다.

URL은 본문 공통 변환에서 절대 http/https 주소인지 확인하고, 커버에서 host 존재와 userinfo 부재를 추가 검사합니다. 이런 표시 위치의 추가 정책은 공통 만료 문법 검사와 구분해 남길 수 있습니다. 근거 S1–S5

공통 조건 · 무엇을 같게 만들 것인가

“없어도 되는 값”이 “틀려도 되는 값”은 아닙니다

아래 세 해결안은 서로 다른 코드 구조입니다. 비교를 위해 만료 정보는 없으면 시각 없이 허용하고, 있으면 정상 시각 문자열인지 검사한다는 개선 규칙을 공통으로 가정합니다. 그러면 숫자 42는 본문과 커버 모두에서 거부합니다.

이 규칙은 아직 적용되지 않았습니다. 기존 본문이 넘어가던 잘못된 입력을 새로 거부하므로, 실제 채택 때는 기존 자료에 미치는 영향을 먼저 확인해야 합니다. 코드 배치만 정리한다고 입력을 허용하는 기준까지 자동으로 결정되지는 않습니다.

  • 정상 글과 만료 정보가 없는 사진의 기존 처리 결과를 보존합니다.
  • 이미 지원하는 종류의 필수 값이 깨지면 실패로 알립니다. 처음 보는 종류는 안내와 자식을 보존하는 기존 처리를 유지합니다.
  • 글을 가져오다 실패하면 일부만 새로 저장하지 않습니다. 마지막 정상 내용과 게시 상태를 유지합니다.
구현 시 보존할 세부 계약: 기본값, 오류 분류, 저장 경계

누락·명시적 null·잘못된 타입·빈 값을 따로 정해야 합니다. 필수이지만 null일 수 있는 항목과 아예 생략할 수 있는 항목은 다릅니다. DTO의 nullable 속성이나 자동 역직렬화만으로 이 구분이 보장되지 않습니다.

설정은 별도 정책을 보존합니다. NotionSettingsMapper.isEnabled의 잘못된 Enabled는 false로 처리합니다. head가 없거나 siteName이 누락되면 기본값을 쓰지만, siteName의 명시적 null·숫자·빈 문자열은 설정 실패입니다. 보기 설정의 누락·null은 기본 옵션을 허용하지만 잘못된 boolean 타입은 거부합니다. 통일 작업으로 이 예외를 모두 실패 또는 모두 기본값으로 바꾸지 않습니다.

공통 외피가 유효한 unknown block은 타입 이름과 자식을 보존합니다. 알려진 paragraph의 rich_text가 숫자인 경우 등 필수 필드 오류는 매핑 실패이며, 예외를 잡아 unknown으로 위장하지 않습니다. 이 블록 정책을 현재 inline 종류의 지원 규칙에 임의로 확대하지 않습니다.

client의 깨진 응답은 현재 CONFIGURATION, 페이지·블록 의미 변환 오류는 MAPPING입니다. HTTP 429·5xx·통신 실패·수집 제한 시간은 RETRYABLE_SOURCE, 401·403은 AUTHENTICATION, 404는 ACCESS, 설정 오류는 CONFIGURATION입니다. 공통 읽기 함수를 써도 각 경계의 오류 분류와 재시도 의미를 보존합니다.

Notion DTO·JsonNode는 어댑터 내부에 남기고, 원본 응답을 저장하거나 로그에 내보내지 않습니다. application 서비스가 짧은 저장 트랜잭션을 소유하며 외부 HTTP 중에는 DB 트랜잭션을 열지 않습니다. 세 안 모두 단일 활성 스케줄러 전제와 단일 배포를 유지하며 새 worker·영속 상태·복잡한 SQL·잠금을 요구하지 않습니다. 근거 S3·S7·S8 및 기준 설계

이미 고친 과거 사례: 공개 주소 검사와 URL 오류 변환

public_url의 엄격한 검증과 URI 예외 변환은 이미 수정되었습니다. 현재 미해결 문제의 예로 세지 않습니다.

현재 requiredNullableText는 public_url의 명시적 null을 정상 미게시 값으로 허용하지만, 누락·비문자열·빈 문자열은 잘못된 응답으로 거부합니다. parseSafeUri는 URISyntaxException을 매핑 예외로 번역합니다. 이력에서 얻을 점은 필드별 규칙과 오류가 전달되는 경계를 명시해야 한다는 것입니다. 근거 S1·S2

해결안 A

블록 종류마다 선언을 실제 읽기 과정에 연결합니다

코드·이미지·문단처럼 종류별로 필요한 데이터 모양을 정하고, 들어온 값을 검사해 그 모양의 값을 실제로 만든 뒤 블로그용 값으로 바꿉니다. 지금 쓰이지 않는 선언을 이름만 유지하는 작업이 아닙니다.

  • 줄 번호 사례가 바뀌는 점: 개발자는 실제 코드 블록의 선언, 이를 읽는 코드, 블로그 값으로 옮기는 코드를 수정합니다. 수정할 선언이 실행 경로에 연결됩니다. 선언에 항목만 추가하고 끝내면 안 되는 점은 여전히 같습니다.
  • 만료값 42 사례가 바뀌는 점: 본문과 커버가 함께 쓰는 미디어 읽기 코드가 값 생성 전에 같은 검사를 합니다. 정상 문자열은 보존하고 누락은 허용하며 숫자는 양쪽 모두 거부합니다.
  • 다음 기능을 넣을 곳: 새 블록 종류에는 그 종류의 데이터 선언과 읽기·변환 코드를 추가합니다. 개발자는 입력부터 저장·표시까지 값이 전달되는지 확인합니다.

비용과 적합한 상황: 종류별로 허용하는 입력을 찾아보기 좋습니다. 대신 새 종류마다 작성하고 맞춰야 할 선언과 변환 코드가 늘어납니다. 블록 종류별 규칙을 명시적으로 관리하고 현재 설계 원칙을 따르는 것이 우선일 때 적합합니다.

A의 구현 범위와 검증

envelope의 열린 type 분기가 종류에 맞는 DTO decoder를 선택합니다. decoder는 필드 존재·타입·기본값을 검사하고, mapper는 DTO를 BlockContent·InlineContent·MediaSource로 바꿉니다. 여러 종류에 무관한 nullable 필드를 한 DTO에 모으지 않습니다. 미디어·리치 텍스트의 공통 DTO도 실제로 재사용합니다.

페이지·설정·데이터 셀에도 같은 책임 구분을 적용하되 설정 기본값과 오류 분류를 보존합니다. unknown type에 알려진 DTO 디코딩을 억지로 시도하지 않습니다. 커버의 추가 URL 정책은 별도 검사로 남깁니다.

자동 역직렬화가 숫자를 문자열로 바꾸거나 누락에 기본값을 넣도록 두면 검사 목적을 놓칠 수 있습니다. Kotlin 기본값과 nullable만 믿지 말고 원래 입력의 존재·타입을 검사해야 합니다. 컴파일러가 속성 타입을 확인해도 새 필드를 실제 화면까지 전달했는지는 보장하지 않습니다.

현재 응답 고정 데이터의 결과 동등성, 누락/null/타입 오류, 공통 미디어 규칙, unknown 보존과 known 실패를 검증합니다. DTO 단독 테스트에서 끝내지 않고 client부터 ImportedPost까지 실제 경로를 확인합니다. 기준 설계 13.6과 가장 직접적으로 맞는 안입니다.

해결안 B

지금 읽는 코드를 기준으로 삼고, 작은 검사 함수를 함께 씁니다

입력에서 필요한 값을 직접 꺼내는 방식을 유지합니다. 대신 쓰이지 않는 선언을 제거하고, “생략 가능하지만 값이 있으면 문자열이어야 한다” 같은 작은 검사 함수를 본문과 커버가 함께 쓰게 합니다.

  • 줄 번호 사례가 바뀌는 점: 따로 남아 있는 미사용 선언을 따라갈 일이 줄어듭니다. 개발자는 코드 블록 값을 직접 읽는 분기에 새 항목과 변환을 추가합니다.
  • 만료값 42 사례가 바뀌는 점: 두 위치가 같은 만료 필드 읽기 규칙을 사용합니다. 정상 문자열·누락·숫자를 구분하므로 숫자를 한쪽만 없는 값으로 넘기지 않습니다.
  • 다음 기능을 넣을 곳: 해당 블록의 읽기 분기를 고칩니다. 개발자는 어떤 검사 함수를 쓸지, 그 블록에서 꼭 필요한 항목은 무엇인지 기억하고 실제 입력으로 확인해야 합니다.

비용과 적합한 상황: 종류별 중간 데이터 선언을 새로 만들지 않아 초기 변경 범위가 작습니다. 대신 입력 항목 이름과 필수 규칙이 직접 읽는 코드에 남습니다. 기능이 많아지면 이 코드가 커지므로, 그 규모와 테스트 부담을 감당하면서 중간 선언을 줄이고 싶을 때 적합합니다.

현재 기준 설계와는 다른 선택입니다. B를 채택하려면 구현 전에 설계 변경이 필요하며, 아직 변경하지 않았습니다.

B의 구현 범위와 검증

미사용 dto/block·dto/richtext를 제거하고 직접 JSON 매핑을 공식 경로로 정합니다. client는 HTTP·공통 외피를, mapper는 type 분기와 의미 변환을 맡습니다. requiredText·optionalNullableText·requiredNullableText처럼 계약이 다른 소수의 읽기 함수를 둡니다.

함수는 도메인이나 HTTP 상태를 알지 않습니다. 실패를 각 경계에서 CONFIGURATION 또는 MAPPING으로 번역하고, 필드별 기본값·커버 추가 정책은 호출자에 둡니다. 작은 함수를 공유해도 매퍼의 JSON 해석과 의미 변환 책임이 자동으로 분리되지는 않습니다.

검사 함수의 입력별 결과와 페이지·본문·커버·설정의 실제 결과를 함께 검증합니다. 종류별 필수 항목과 필드 이름은 컴파일러만으로 확인할 수 없으므로 응답 고정 데이터가 필요합니다. 최종 구조에 종류별 DTO를 두지 않는 것이 A와의 차이입니다.

해결안 C

사진과 꾸민 글자처럼 반복되는 자료부터 함께 읽습니다

모든 블록의 선언을 먼저 만들지 않습니다. 여러 곳에서 반복되는 미디어·글자 꾸밈 자료의 모양과 읽기 코드를 묶어 실제로 사용합니다. 각 블록에만 있는 항목은 그 블록에서 직접 읽습니다.

  • 줄 번호 사례가 바뀌는 점: 코드 블록만의 옵션이므로 그 블록의 직접 읽기 코드를 고칩니다. 쓰이지 않는 옛 선언은 연결할 형태로 바꾸거나 제거해 혼동을 줄입니다.
  • 만료값 42 사례가 바뀌는 점: 본문과 커버가 공통 미디어 읽기 코드를 거쳐 검사된 값을 받습니다. 만료 규칙을 한곳에서 고치면 두 위치가 함께 적용받습니다.
  • 다음 기능을 넣을 곳: 새 사진 블록은 공통 미디어 읽기를 재사용하고 고유 항목만 따로 읽습니다. 여러 기능이 실제로 같은 자료를 쓰기 시작할 때 그 부분을 공통 모양으로 묶습니다.

비용과 적합한 상황: C는 여러 곳에서 반복되는 자료만 공통 선언과 읽기 코드로 묶고, 각 블록에만 있는 항목은 직접 읽는 구조를 유지합니다. A도 사진부터 차례로 적용할 수 있지만, 최종적으로는 블록 종류마다 선언과 읽기·변환 코드를 연결해 관리합니다. C는 관리할 선언의 범위를 줄이는 대신, 개발자가 “함께 읽는 항목”과 “각 블록에서 직접 읽는 항목”의 경계를 계속 지켜야 합니다. 미디어와 글자 꾸밈처럼 반복되는 부분을 중심으로 관리하고 싶을 때 적합합니다.

현재 기준 설계와는 다른 선택입니다. C를 채택하려면 구현 전에 설계 변경이 필요하며, 아직 변경하지 않았습니다.

C의 구현 범위와 검증

공통 media decoder가 file/external 구분, URL 문법, 만료 필드 존재·타입을 소유하고 mapper가 MediaSource를 만듭니다. body·cover·icon이 이 결과를 쓰며 커버 선택·추가 URL 정책은 커버 reader에 남깁니다. rich-text decoder는 annotations와 text/equation/mention의 모양을 읽습니다.

envelope·동적 property map·드문 블록의 고유 payload는 JsonNode로 유지합니다. 설정·데이터 셀의 동적 속성은 엄격한 필드 읽기로 처리합니다. 같은 미디어를 일부 호출자만 직접 읽기 시작하면 규칙이 다시 갈라지므로 공통 코드를 거치는지 검증해야 합니다.

공유 decoder의 입력별 검사와 모든 사용처의 결과를 확인하고, 남은 직접 읽기 코드에서도 알려진 타입의 오류가 실패로 전달되는지 검증합니다. 관계없는 필드를 하나의 nullable 속성 모음에 합치지 않습니다. 최종 목표는 공유 모양과 직접 읽기의 구분을 유지하는 것이며, A로 가기 위한 임시 단계만을 뜻하지 않습니다.

  2. 어떤 잘못된 입력을 거부할지 정합니다. 기존에 통과하던 자료가 새 규칙으로 실패하는 영향도 따로 확인합니다.
  3. 선택한 구조로 사진 한 경로를 끝까지 연결하고 모든 사용처를 확인합니다. 이후 새 블록과 옵션을 같은 방식으로 추가합니다.
  4. 쓰이지 않는 선언을 정리한 뒤 정상 글, 오류 처리, 마지막 정상 내용 보존을 확인합니다. 실제 구현 때는 저장소 규칙에 따라 실패 테스트부터 작성하고 관련·전체 테스트와 build를 실행합니다.
기준 설계 13.6과 구현의 차이: B/C를 선택할 때 먼저 바꿀 문서

현재 13.6은 envelope payload를 type에 맞는 어댑터 내부 DTO로 명시적으로 디코딩하고, JsonNode를 그 사이에서만 쓰도록 규정합니다. 실제 블록 매퍼는 type 분기에서 JSON을 직접 읽으므로 이 부분은 이미 기준 설계와 차이가 있습니다.

A는 구현을 현재 기준으로 맞춥니다. B는 직접 매핑의 경계로 규정을 바꿔야 합니다. C는 공통 모양의 decoder 책임과 JsonNode가 남는 범위를 명시해야 합니다. B/C를 위한 설계 13.6 수정은 아직 미완료이며, 실제 채택 시 구현보다 먼저 해야 합니다. 이번에는 기준 설계 문서를 수정하지 않았습니다.
